Step Framework

The Steps app is the plug-in framework for every action a workflow can perform — it was my main area of ownership. I extended the registry architecture and built steps on top of it, from the webhook trigger through to dynamic input types, credential handling, and step replay.

The registry architecture I worked with and extended

  1. Discovery — at startup, the registry scans the steps/ directory and imports every step implementation.
  2. Validation — each implementation is checked against framework requirements: required methods and input/output schemas must be present.
  3. Registration — compliant steps are stored as a type-string → class mapping, with metadata (step type, version, capabilities).
  4. Runtime resolution — during workflow execution, steps are resolved by type: fast lookup, instance creation, dependency injection, and execution-context setup.

Integration steps I built on the framework

  • Webhook trigger — one of my first backend contributions; external systems can start a process run via HTTP callbacks.
  • HTTP request step with pagination — generic REST integrations, including paginated API traversal.
  • Google Sheets — append rows, create worksheets on the fly, validate sheet data, plus a later refactor of the step.
  • Salesforce — integration step including password-flow authentication.
  • Slack — steps supporting the platform onboarding flow.
  • Hubstaff — improved token-refresh reliability using a shared ICB cache.
  • SkySlope — CEM/listing-review steps, fetching listing files, persisting service sessions.
  • GrubHub "create menu" pipeline — a multi-step third-party API flow (job submission, normalized menu building, link isolation, sheet validation, completion handling on 403s).
  • Email outreach & LLM chat hardening — custom outreach steps, credential input fixes, and allowlisting GCS-prefixed URLs in the LLM chat step.

ProcessGPT — AI Workflow Generation

ProcessGPT is the AI assistant that turns chat conversations and uploaded documents into valid, executable workflow definitions. My work sat at the seam between the AI system and the step framework.

The generation pipeline

  1. Conversation routing — classifies the user's intent: generate a workflow, answer a question, or ask for clarification.
  2. Context gathering — retrieves relevant step templates (BM25 keyword search), similar past workflows (vector search), and chunks from the user's uploaded documents (RAG, backed by a Temporal-orchestrated PDF ingestion pipeline).
  3. High-level workflow generation — the LLM drafts the workflow structure: stages, steps, edges, and triggers as JSON.
  4. Detailed generation — expands the draft into the complete process DSL, stage by stage, including patch-based edits for existing workflows.
  5. Validation — the output is parsed and validated against the Pydantic process definition schema before anything else happens.
  6. Critic loop — a second LLM call reviews the draft for connectivity, dangling references, and completeness, returning approve or retry with feedback; feedback is fed back into generation.

Guardrails the system uses (zero fine-tuning)

  • Strict structured output — strict JSON-schema response formats constrain the model to workflow-conforming JSON only.
  • In-prompt DSL grammar — the exact DSL shape (stages/steps/edges/triggers) plus a complete few-shot example workflow is injected into every prompt.
  • Server-side ID generation — ID suffixes are generated by the server and handed to the model, preventing hallucinated or colliding step IDs.
  • Pydantic validation + critic loop — every draft is schema-validated, then reviewed by a critic LLM that can reject and regenerate with targeted feedback.
